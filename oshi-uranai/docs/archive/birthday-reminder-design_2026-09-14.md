# 誕生日メール設計書

作成：2026-08-27／**最終更新：2026-09-14（登録直後メール＋誕生日メールの2段構成へ。本文は部品方式）**

インスタのフィード投稿（誕生日投稿）から有料の出生図鑑定までをつなぐ、
メール配信の仕組み。登録は1回、**初年度2通・以降は年1通**。

---

## 1. なぜ作るか

### 解決したい課題

フィード投稿のリーチは既存フォロワー中心。そこに毎日「プロフィールのリンクから」を
置いても、すでにアプリを知っている人には無効。かつリンク先（無料アプリ）が
商品になっていないため、クリックされても売上につながらない。

### この仕組みが効く理由

誕生日は相手ごとにバラバラな「確定した日付」。
受け取る側が日付を知っていて、しかもその日が本人にとって特別なので、
開封率が構造的に高い。かつ年1回なのでCTAが摩耗しない。

「推しの誕生日」も登録できるようにすると、発火回数が年に数回へ増え、
同担へのシェアも起きる（フィードでは起きにくかった外向きの拡散）。

## 2. 情報の段差（設計の核）

3段がそれぞれ「別の種類の情報」を持つこと。量が増えるのではなく種類が増える。

| 段 | 読めるもの | 必要な情報 | 価格 |
|---|---|---|---|
| フィード投稿 | 太陽のみ（1天体） | 月日 | 無料・誰でも |
| **誕生日メール** | **10天体＋年齢の節目** | **＋生まれ年** | **無料・登録者** |
| 出生図鑑定 | ＋ASC・MC・ハウス | ＋時間・場所 | 有料 |

### 生まれ年が加わると何が読めるようになるか

1. **太陽以外の9天体**（最重要）
   同じ9月4日でも生まれ年が違えば水星・金星・火星は別のサイン。
   1天体→9天体で情報量が桁で変わる。

2. **デーカン所属の確定**
   同じ日付でも太陽の度数は年により最大1.18度ずれる（1950-2010で実測）。
   - 8/31：61年すべて「前半」
   - 9/2 ：60年が「前半」、1年だけ「真ん中」
   - 9/3 ：55年が「真ん中」、6年は「前半」
   境界日生まれの人は、生まれ年によって性格の軸そのものが入れ替わる。

3. **年齢でしか来ないイベント**
   土星回帰（29-30歳／58-60歳）、木星回帰（12年ごと・24/36/48歳前後）、
   天王星の衝（42歳前後）。生まれ年がないと絶対に出せない。

4. **進行の太陽**（約30年で隣のサインへ）
   「昔と好みが変わった」に説明がつく素材。

### 登録ハードル

生まれ年は誰でも答えられる。時間と場所は思い出せない人が多い。
**先に年だけもらう**のが、いまのCTA（時間と場所）より通る。

**納品はメール一本（2026-08-27 決定）。** 当初あった「鑑定のお届け先＝InstagramのDM/メール」の
選択は削除した。DMを外した理由：

- DMは1通1000字まで。オーダーメイド鑑定は必ず超えるので分割送信になる
- こちらから送ると相手の「メッセージリクエスト」に入り、気づかれないことがある
- 保存も検索もできず、あとから読み返せない
- **DMを選んだ人はメール欄が空になり、リマインド名簿から丸ごと落ちていた**（実データで確認）

Instagram IDは納品手段ではなく **メールが届かなかったときの予備連絡先** として任意で残す。
メールアドレスは全員必須にし、これで申込者は必ず名簿に載る。

⚠️ オプトインのチェック（誕生日リマインド）は **必須にしないこと**。
必須にすると同意が強制になり、任意の同意を前提とする特定電子メール法の趣旨に反する。
かつ、望まない人が鑑定を申し込めなくなる。

### ⚠️ 鑑定の実体は「フォーム寄り」

`natal-reading-design.md` は500字・素材のスコアリング自動選定を前提にしているが、
**実際の個人鑑定は悩み起点のオーダーメイド**（ユーザー確認済み・2026-08-27）。
Bフォームの「モヤモヤ」「読んでほしいテーマ」「触れてほしくないこと」が本体。

→ `natal-reading-design.md` 3章の素材選定スコアリングは、この方針とはずれている。
　 出生図は「読みの土台」として使い、**構成は相談内容に合わせて可変**にする。
　 分量・価格・所要時間も量産型より重くなる前提で設計し直すこと。

## 4. 配信タイミング

| タイミング | 内容 | 役割 | 頻度 |
|---|---|---|---|
| **登録した直後** | 層1 性格の軸＋層2 いま動いている1年の骨格＋節目 | **売らない回**（価値を先に渡す） | 初年度に1回だけ |
| **誕生日の当日** | おめでとう＋層2 今年の骨格＋層3 滑り出し＋層4 その日の空気＋節目<br>**罫線の下に**鑑定の案内 | 祝う回。案内は添えるだけ | 毎年 |
| **推しの誕生日3日前** | 「◯◯さんの誕生日、もうすぐです」 | シェアが起きる回 | 該当者のみ |

### なぜこの順番か（2026-09-14 確定）

**登録直後に読みを渡し、誕生日に案内する。** 案内が届くころには「この人の読みは役に立つ」が実証済みになっている。

ここに至るまでに2回変えている。経緯を残しておく。

| 版 | 構成 | やめた理由 |
|---|---|---|
| 初版 | 5日前に売る回／当日は売らない回 | おめでとうの直前に売られるのが気まずい |
| 2版 | 当日は売らない回／14日後にフォローで売る | **当日に登録した人が1年待たされる。**年1回しか接点がないのに売る回を別便にすると通数が増える |
| **現行** | **登録直後に渡す／誕生日に祝って、罫線の下で案内** | — |

### 層の割りふり（2026-09-14 確定）

| 層 | 登録直後 | 誕生日 | 何で決まるか |
|---|---|---|---|
| 1 性格の軸 | ○ | ✕ | 太陽サイン×デーカン。毎年同じ文なので、毎年送ると「去年と同じ」になる |
| 2 年の骨格 | ○ | ○ | 木星・土星→出生太陽。登録直後は**直近の誕生日**、誕生日メールは**その日**が起点 |
| 3 滑り出しの色 | ✕ | ○ | 水星・金星・火星→出生太陽。**誕生日起点**の文言 |
| **3' いまの数週間** | **○** | ✕ | 層3と同じ天体を**登録日**で計算。層3の代わり |
| 4 その日の空気 | ✕ | ○ | 誕生日当日の月 |
| 4' 登録した日の月 | — | — | 書いてあるが**未使用**（`parts.md` に保存。戻すなら moon_block を復活） |
| **木星の12年周期** | **○** | ✕ | 出生木星からの角度÷30度。**アスペクトが無い年でも必ず1本出る**ので、ここが「来年の話」の受け皿 |
| **備え（今年やること）** | **○** | ✕ | 来年の段階に対する今年の行動。**周期の文と同じ段落**で続ける |
| ＋節目 | ○ | ○ | 木星・土星・天王星。その時点の起点で計算し直す |
| ＋次に来る節目 | ○ | ✕ | 次の節目を**年齢と西暦**で予告。生まれ年が無いと出せない＝情報の段差の証明 |

**登録直後メールの年運は「直近の誕生日」を起点にする。** 次の誕生日ではない。
いま動いている1年の話でないと、読んだ人が照合できない。

**「薄い年」が必ず出る。** 木星も土星も当たらず、節目も無い年がある（実測：1977-07-27生まれの2026年は層2が1本のみ）。
アスペクト頼みだと本文が2段落で終わるので、**必ず1本出る段（木星の12年周期）を入れて底上げしている。**

### 着地は「来年こうだから、今年はこうする」

来年の段階を出して終わらせず、**今年の行動に落とす**。同じ段落で続ける。

> 人が増える年です。外から声がかかりやすく、行き先が自分の予定の外から来ます。断らずに一度会ってみるといい年。
> **なので今年は、できるだけ自分の世界を広げておくことをおすすめします。来年声をかけてくれる人は、今年広げた範囲から来ます。**

### 送る形（2026-09-14 実測でわかったこと）

- **本文は1行30字前後で、句点（。）のところで折る。** 折らずに送ると受信側の画面幅まで伸び、単語の途中で改行される。
  読点でも折ると短い行が続いて歯抜けに見えるので、**句点だけ**で折る
- 書き出しは `oshi-uranai/mail/out/*.txt`。**件名の行は含めない**（そのまま貼れる本文だけ）
- **貼り付けは `Ctrl + Shift + V`。** エディタから普通にコピーすると、シンタックスハイライトの
  文字色と背景色がHTMLごとコピーされ、Gmailで黒背景になる

### 売り方の作法

祝いと売りを同じ文面で混ぜない。**誕生日メールは本文を「いい一年になりますように。」で閉じ、
罫線（⸻）の下に案内を置く。** 祝いの文章の中に鑑定の話を入れない。
この一線を外すと、初版の5日前メールをやめた理由に戻る。

## 5. 本文はどこから来るか

### 恒久資産と、毎年作り直すもの

| 層 | 中身 | 毎年変わるか |
|---|---|---|
| 1 性格の軸 | デーカン36本ストック（`daily/sun-decans.md`） | **変わらない** |
| 2 この1年の骨格 | 木星・土星→太陽 | **毎年変わる** |
| 3 滑り出しの色 | 水星・金星・火星→太陽 | **毎年変わる** |
| 4 誕生日の空気 | 当日の月のサイン | **毎年変わる** |

木星は約12年周期、土星は約29年周期。
**「366日分たまれば以後ゼロ」にはならない。** 恒久資産は36本のデーカン本文と
生成の型・スクリプトであって、366本の完成テキストではない。

### 本文の出どころ（2026-09-14 変更）

**旧：その年のフィード投稿の本文が、そのまま当日メール本文になる。**
→ 366日誕生日投稿が**凍結**された（再開ラインFW3,000）ので、この前提は成立しない。
フィード投稿を待つと、当日メールの本文が永久に来ない。

**新：部品を組み合わせて、スクリプトが本文を組む。**

| 層 | 部品の置き場所 | 本数 |
|---|---|---|
| 1 性格の軸 | `oshi-uranai/ig-daily/sun-decans.md` | **36本**（作成済み・レビュー待ち） |
| 2 年の骨格 | `oshi-uranai/mail/parts.md` 木星・土星 × 5アスペクト | 10本 |
| 3 滑り出し | 同上 水星・金星・火星 × 5アスペクト | 15本 |
| 4 当日の空気 | 同上 月のサイン12 | 12本 |
| ＋節目 | 同上 木星リターン／土星3局面／天王星オポジション | 5本 |

合計**78本**。**366本ではない。** 一度書けば毎年使い回し、名簿が増えても本数は増えない。
組み合わせと計算はスクリプトがやるので、同じ誕生日の人でも年が違えば本文は変わる。

**全部を先に書く必要もない。** その月に誕生日が来る登録者に当たった部品だけあればよく、
無い組み合わせは出力に `【未執筆：木星・トライン】` と出る。埋めれば部品が1本増える。1年回せば自然に埋まる。

**部品は2026-09-14にレビュー済み（`sun-decans.md` は無修正で承認、`parts.md` は木星3本を修正）。** 以後は未執筆の穴を埋めるときだけ触る。

### 登録者だけの一段

当日メールの末尾に、**生まれ年があるから書ける一文**を必ず足す。

> 今年は◯◯さんにとって、木星が生まれたときの位置へ戻る年です。
> 12年に一度。世界が少し広がる番が回ってきました。

ここが薄いと「インスタと同じ」になり、登録の意味が消える。
対象は当日誕生日の数人なのでスクリプトで回せる規模。

## 6. 実装

### 構成

```
Googleフォーム → スプレッドシート（統合名簿）
                      ↓ CSVで書き出し
        ローカルPython（birthday_mail.py）… 天体計算と本文の組み立て
                      ↓ TSVを「配信待ち」タブへ貼る（＝ここで赤入れする）
        GAS（毎朝7時トリガー）… 今日の日付の行を送るだけ
                      ↓
                   Gmail送信
```

**GASに天体計算をさせない。** GASではSkyfieldが動かないため、計算はローカルのPython、GASは配送だけにする。
market-mailer（朝の相場レポート）と同じ分担。

### 2つの運用（登録直後は都度／誕生日は月初）

```bash
# 登録が入ったとき（1人ぶん・その場で作って、赤入れして送る）
python oshi-uranai/mail/birthday_mail.py --welcome --birth 1981-09-19 --name ゆか --email a@example.com

# 取りこぼしの埋め戻し（名簿の全員ぶんの登録直後メール）
python oshi-uranai/mail/birthday_mail.py --welcome --meibo meibo.csv

# 月初：その月に誕生日が来る人の誕生日メールを一括で
python oshi-uranai/mail/birthday_mail.py --month 2026-10 --meibo meibo.csv

# 部品の埋まり具合だけ見る
python oshi-uranai/mail/birthday_mail.py --check-parts
```

**登録直後メールは待たせない。** 登録が入ったらその場で作って送る。バッチに乗せない
（バッチに乗せると、当日に登録した人が待たされるという2版の失敗が戻る）。

**誕生日メールは月初に10分。**

1. 出てきた本文に赤入れする（`【未執筆：…】` の穴を埋める＝部品が1本増える）
2. `oshi-uranai/mail/out/配信待ち_YYYY-MM.tsv` をスプレッドシートの「配信待ち」タブに貼る
3. あとは触らない

スクリプトが出す警告：**デーカンの境目**（太陽が10度・20度の前後1度）と**サインの境目**（0度・29度台）。
ここに当たった人は、生年によって使うストックが変わるので手で確認する。

### GASの処理（毎朝7時）

```
1. 今日の日付を取得
2. 「配信待ち」タブから 送信日 == 今日 の行を抽出
3. 送信ログを照合し、既送信ならスキップ
4. 件名と本文をそのまま送信（差し込みも計算もしない）
5. 送信ログに記録
```

該当0件ならそのまま終了。コードは30行程度。**未作成**（名簿20件たまるまでは手動送信）。

### コストと手間

| 項目 | |
|---|---|
| 初期構築 | フォーム＋シート＋GAS で半日〜1日 |
| ランニング | 0円（GAS無料枠・1日100通まで） |
| 運用 | 週次バッチを回す以外はゼロ |

### LINEを使わない理由

日付ごとの個別配信には Messaging API が必要で、無料枠が月200通と厳しい。
**メールから始める。**

## 7. 初期名簿

**2年前の無料お試し鑑定申込者が、すでに生年月日を渡してくれている。**
これが初期名簿。出生図鑑定の設計書がそもそも彼ら向けの再アプローチ用なので、
話が一直線につながる。

再アプローチ文面の方向：

> 2年前、鑑定に申し込んでくださった方へ。
> あの時いただいた生年月日で、今年の誕生日にお手紙を送る仕組みを作りました。
> いらなければこのメールの下から解除できます。

売り込みより角が立たない。

## 8. 法務・プライバシー

- **オプトインの証跡**：フォームに同意チェック、登録日時をシートに保存（特定電子メール法）
- **配信停止リンク**を全メールのフッターに必須。ワンクリックで除外フラグが立つ形に
- **送信者表示**：氏名または名称・住所・問い合わせ先を明記
- **生年月日＋メールは個人情報**。シートの共有範囲を絞る。フォームにプライバシーポリシーを添える
- 呼び名は本名でなくてよい旨をフォームに明記する

## 10. フィード側のCTAローテーション

7日全部同じ固定文は既存フォロワーには背景ノイズになる。

| 頻度 | 内容 |
|---|---|
| 週2日（骨格が強い日・イベント日） | 有料鑑定 or 登録へ |
| 週3日 | 「保存してね」「今日誕生日の人にシェア」だけ |
| 週2日 | 「あなたの誕生日はいつ？コメントで」（エンゲージメント＝リーチ拡大） |

**売らない日を作るほうが、売る日のCTAが効く。**

## 11. 進め方

1. **Googleフォームを1枚作る**（3章の項目設計。実物の仕様は `birthday-reminder-form-spec.md`）
2. **フィードCTAを週1〜2回フォームへ向ける**
3. **名簿が20件たまったらGASを書く**
   （それまでは手動送信で十分。むしろ手動でやると文面が磨ける）
4. 既存の無料お試し申込者へ再アプローチ

**先にフォームだけ作ってCTAを流すのが順番として正しい。**
仕組みは後から追いつけるが、集め始めるのが遅れた分は取り返せない。

## 12. スケジュール（2026年9月）

**動かせない日付は 9/30（有料鑑定を9月中に開始）だけ。** それ以外に締切はない。

| 週 | やること | 実作業 |
|---|---|---|
| 〜8/30 | **A：登録フォームを作って公開**。プロフィールにリンク | 20分 |
| 9月1週 | フィードCTAのローテーション開始（10章）。登録が集まり始める | 週次バッチのついで |
| 9月2週 | 鑑定の価格を決める。**B：申込フォームを作る**（Aの複製＋時間・場所を必須化） | 半日 |
| 9月3週 | 2年前の申込者へ再アプローチメール（7章） | 半日 |
| 9月4週 | 最初の数件を手動で納品。文面を磨く | 都度 |

実作業の合計は1日ちょっと。

### Aだけ先に抜く理由

**名簿は時間で貯まるものなので、公開が遅れた分は取り返せない。**
今週公開すれば9月末までに1ヶ月分たまる。9月末に公開したらゼロ。作業は20分。

逆に **B（有料鑑定の申込）は急ぐ意味がない。**
9月末の公開でも「9月中に開始」は満たせる。それまでにAで見込み客が見えていれば、
価格も文面も判断しやすくなる。

### AがBの見込み客リストになる

Aフォームの Q3〜Q5（生まれた時間帯・正確な出生時刻・生まれた場所）は任意にしてあるが、
**ここまで書いた人＝出生図鑑定の必要情報を全部渡している人**＝購入意向の強いシグナル。

9月にBを始めるとき、この人たちに個別で声をかければ最初の数件は取れる。
Aは名簿収集であると同時に、Bの見込み客の選別装置。
